etl2d — Notes

etl2d: geographic data moved and transformed by drawing a graph of boxes, in the spirit of FME, built on GDAL/OGR, in Python, with Dear ImGui. Each box is a node; nodes are found in folders at start, as ComfyUI's custom nodes, so anyone adds one by dropping a Python file. A sibling of render2d and carto2D: render2d draws the previews. This document comes before the code; when in doubt, it is authoritative.

1. The idea

Four draughtsmen correct façades and address points in MicroStation; FME squeezes the files into Oracle tables. FME does it by a graph: a reader, transformers, a writer, joined by lines, and data flowing through. It is powerful and expensive. etl2d does the common part of it with free tools: GDAL/OGR reads and writes every format (shapefile, GeoPackage, FlatGeobuf, PostGIS…), PROJ reprojects, Python glues, and a node editor draws the graph.

Directory reader (UrbIS, *.shp) ─► Attributes ─► Clip (Grand-Place) ─► Reproject (31370 → 3812) ─► Writer (GeoPackage)
                                                      └─ outside ─► Writer (rejects.fgb)

What it borrows:

  • From FME: features flowing one by one (§3), the structure known before the data (§4), the names of its common transformers (AttributeManager, Reprojector, Clipper, PythonCaller).
  • From ComfyUI: nodes found at start in folders, a node = a Python class (§8); a workflow saved as a JSON file and run again without the window (§10).
  • From carto2D: Dear ImGui and its docking (the same look), the navigation of the map (its notes §9 to §11) for the previews, drawn by render2d.

What it is not, at first: a replacement for PostGIS (the heavy spatial joins stay in the base, where an index does them), nor a scheduler (a workflow runs when asked).

2. Installing: Python and a .venv

As ComfyUI: an official Python from python.org (3.12 or later), and a .venv folder inside the project holding everything else. Nothing installed system-wide, nothing to conflict with another program; to start again, delete .venv.

  • GDAL for Python is the delicate part on Windows: PyPI publishes only its sources (building them needs a compiler and GDAL's own libraries). Christoph Gohlke builds ready wheels of GDAL for Windows, served by a pip index: pip install --index-url https://gisidx.github.io/gwi gdal (Python 3.12 to 3.15, 64-bit). That is the whole GDAL: ogr, osr, its formats, PROJ inside.
  • The window: imgui-bundle from PyPI: Dear ImGui, imgui-node-editor (the graph), ImPlot (charts, later), the docking.
  • render2d is not installed in the .venv: etl2d calls render2d.exe (the release zip, or the one installed with carto2D), its folder given once in the settings. Its GDAL and etl2d's do not meet: they exchange files only.
setup.bat      python -m venv .venv, then pip install -r requirements.txt (GDAL from Gohlke's index)
run.bat        .venv\Scripts\python -m etl2d

On Linux (the CI, the agent's machine), GDAL's bindings come from the system's packages or from pip with GDAL installed; the code is the same.

3. Features flow one by one

A node does not wait for the whole layer: it receives a feature, does its work, passes it on. In Python this is a generator: a function that gives its results one at a time with yield, and stops in between until asked for the next one.

def run(self, features):              # a Clip node, much simplified
    for f in features:                # asks the node before for one feature, then waits
        if f.geometry.Within(self.box):
            yield f                   # gives it to the node after, then waits to be asked again

The writer pulls: it asks the clip for a feature, the clip asks the reprojector, the reprojector asks the reader, which reads one from the file. Then back up the chain. Only a few features are in memory at any time.

663,358 UrbIS addresses through Reader → Clip → Writer
  1. All at once: every address in memory before the clip starts. An OGR feature of 17 fields and a point weighs some hundreds of bytes in Python; 663,358 × 500 bytes ≈ 330 MB, before anything is written.
  2. One by one: a handful of features in memory; the first ones are written while the last are not yet read.
  3. The time: Python handles some tens of thousands of features per second through a few simple nodes. At 20,000 a second: 663,358 ÷ 20,000 ≈ 33 s. For an ETL that runs when asked, acceptable.
Measured at step 1 (16 November)
  1. 200,000 address-like points (3 columns) through Reader → Attributes → Clipper (the Grand-Place: 23,675 inside) → Reprojector → Writer (GeoPackage): 4.8 s, 200,000 ÷ 4.8 ≈ 41,000 features read a second, twice the estimate.
  2. Where the time goes (Python's profiler): about three quarters in the reader, turning each OGR feature into an etl2d Feature (its fields one by one, its geometry cloned). The clip's test: about 5 %.
  3. The 663,358 addresses would then take some 16 s. If one day it is too slow: GDAL can hand a whole batch of features at once (its Arrow interface), and the reader would build Features from batches.

That is also what makes the Python caller natural (§7): one function, one feature in, zero, one or several out.

Some nodes cannot work one by one: a sort, a group-by, "the 10 largest". They read everything first (into memory or a temporary file) and give the result after. They say so in the node (a small mark), so that the graph's cost is visible.

4. The structure travels before the data

In FME, when a column is removed, the next transformer's list of columns is already up to date, without running anything. etl2d does the same: each node declares two functions.

schema(inputs) -> outputs     the structure: columns, geometry type, system. Instant; called at every change of the graph.
run(inputs)    -> outputs     the features. Called when the workflow runs.
The UrbIS addresses, structure only
  1. The reader opens the shapefile's header (no feature read): 17 columns (PARENTID, a String of 88 characters; STRNAMEFRE, the street name in French; POLICENUM, the house number…), points, EPSG:31370, 663,358 features.
  2. The attribute manager drops PARENTID, renames STRNAMEFRE to street, adds source String 20 = 'UrbIS 2026': 17 − 1 + 1 = 17 columns, one renamed. Shown at once in its node.
  3. The reprojector changes the system only: EPSG:3812.
  4. The writer knows, before any run, the table it will create: 17 columns with their types, points, EPSG:3812. A mistake (a column name longer than the 10 characters a shapefile allows, a limit of its DBF of 1983) is said in the node, in red, before the run.

A schema is a small object: the list of columns (name, type, width), the geometry type, the system (WKT), and the count when known. It is what the node editor shows on each link when the mouse is over it.

5. The needs come up

The structure goes down the graph (§4). The needs come up: from the writers to the readers, each node says which part of the features it will use, and the reader asks its source only for that. A database does the same when it pushes its filters and its columns down to the table.

The UrbIS buildings clipped to the Grand-Place (16 November)
  1. Without: the reader reads the 247,625 buildings and turns each into a Feature; the clip keeps 1,356. 44 s with the shapefile on the NAS, 6 s on a local disk.
  2. With: the clip says "only what touches 148,500 170,400 149,300 171,000"; the reader passes the box to the source, which uses its spatial index (a shapefile's .qix, a GeoPackage's R-tree, PostGIS's GiST). Only the buildings near the Grand-Place are read.
  3. On the test file of §3 (200,000 points, a GeoPackage): 4.8 s became 1.15 s, 23,691 features read instead of 200,000, without anything written by hand in the workflow.

Two things come up

  • A box: only the features near it are needed. None: all of them.
  • Columns: only these are used. The reader tells GDAL to ignore the others (SetIgnoredFields, as render2d does for its styles, its §30) and builds the Features with those only. None: all of them.

The box through the reprojector
  1. A clip after a Lambert 72 → Lambert 2008 reprojector asks the box 648,500 670,400 649,300 671,000 (Lambert 2008). A Lambert 72 file knows nothing of it.
  2. The box's edges are taken back to Lambert 72, 21 points on each (a straight edge in one system is slightly curved in another): about 148,500 170,400 149,300 171,000, to a few decimetres (the change of datum, §7).
  3. 1 % of margin around: 8 m on 800 m, 6 m on 600 m: 148,492 170,394 149,308 171,006. Nothing near the edge is lost; the clip's exact test does the rest.

In code

A third function beside schema() and run(): needs(wanted) receives, per output, what the nodes after it need (a Needs(bbox, columns)), and returns what it needs per input. The graph calls them backwards, writers first, just before running (plan_needs()); a reader finds in self.wanted what to ask. etl2d run prints it under each reader: "asked to the source: box 148500 170400 149300 171000, 2 of 3 columns".

6. A feature in etl2d

class Feature:
    attributes: dict[str, object]     # 'street': 'Grand-Place', 'POLICENUM': '12'...
    geometry:   ogr.Geometry | None   # GDAL's own: no conversion between nodes
    fid:        int | None            # its number in the source
    source:     str                   # the file it came from (the directory reader sets it)
  • The geometry stays GDAL's (ogr.Geometry): reading, reprojecting, clipping and writing are GDAL's own operations, so it never changes form on the way. A Python caller that prefers another library converts it itself (WKT, WKB).
  • The attributes are a plain dictionary: what a Python caller expects to read and write, without knowing OGR.
  • The structure is not repeated in every feature: it is the link's schema (§4).

7. The first nodes

Reader

A file or a connection (PG:host=… dbname=…, the password never written, as in carto2D §65), and a layer when the source has several. Its node shows the structure (§4), the count, the extent, the system. Option: a bounding box asked to the source itself (SetSpatialFilterRect), which uses its spatial index: the clip that follows then sees only the features near the box.

Directory reader

A folder, a pattern (*.shp), sub-folders or not. Every file found is read in turn, all into one flow; a column source_file is added (FME's fme_basename). Files of different structures (a delivery per municipality, one with a column more): the structure is the union of all, a missing value is empty, and the node lists the differences, file by file, column by column.

Ask the source first (both readers: their bbox). Tried on 16 November: the 247,625 UrbIS buildings, a shapefile on the NAS, clipped to the Grand-Place: 1,356 kept, 44 s, because every building was read and turned into a Feature only to be thrown away by the clip. With the reader's bbox set to the clip's box, the source gives only the buildings near it (with its index: the .qix of a shapefile, made by qix.bat, or a GeoPackage's R-tree); on the test file of §3, 4.8 s became 2.2 s. Since 0.1.3 the clip hands its box up to the reader by itself (§5): the reader's own bbox is for a box no clip states.

Attributes (FME's AttributeManager)

The columns received, one row each: a box to keep it, its name to rename it, its type; a "+" for a new column with its type and a value (a constant, or an expression on the others, later). The order of the rows is the order written.

Expressions: computed columns, without Python 0.6.0

In Attributes, a new column's value that begins with = is computed for each feature, as in a spreadsheet; without = it stays a constant (UrbIS 2026). A row named as a column that arrives replaces its value (area = = round(area)). FME's AttributeCreator and ExpressionEvaluator in one place. Later, the same expressions as the Filter's rules (a comparison "is true").

On a real building of the Grand-Place (fid 9, inspire_id …/building/1642208, its column area = 103, in EPSG:3812)
  1. = area * 2 → 206
  2. = round(area / 10) * 10 → 103 / 10 = 10.3, rounded 10, × 10 = 100: areas to the ten.
  3. = area() → 103.16: the area computed from the geometry, in m² of the system; area without brackets is the column (the official area, 103). Two names, two things: the brackets say "computed".
  4. = length() → 48.56: a polygon's perimeter (a line's length).
  5. = npoints() → 12: 11 corners, plus the last point that closes the ring (the same as the first).
  6. = x(0) → 648,583.02, = y(0) → 670,888.42: the first point.
  7. = if(area >= 200, 'large', 'small') → small.
  8. An address: = strnamefre || ' ' || policenum → Grand-Place 14.
Run on the whole GeoPackage (16 November, 0.6.0): the six columns above on the 1,356 buildings and the label on the 4,662 addresses, 0.59 s; the building fid 9 gives back exactly 100, 103.16, 48.56, 12, 648,583.02 and "small".
Counting from zero

x(0) is the first point, x(1) the second, x(14) the fifteenth; the last is x(npoints() - 1), or x(-1) (a negative number counts from the end, as in Python: x(-2) the one before the last). The same for substr(text, 0, 3): the first three letters. As Python, FME and GDAL count; chosen on 16 November, for its first user, who codes.

And beware of rings: a polygon's last point repeats its first. On the building above, npoints() = 12 for 11 corners, and x(11) = x(0). The points are counted through every part and ring, in their order: the outer ring of the first polygon, its holes, then the next polygon.

Empty values: a calculation with an empty value (NULL) gives NULL (area * 2 on a building without area: empty, not an error); a comparison with NULL is false, as in the Filter; coalesce(area, 0) gives 0 for the empty ones. x(30) on a geometry of 12 points: NULL, and a note on the node counting how many.

Said before running (§4): a column that does not arrive, a function that does not exist, a bracket missing, the place of the mistake shown (= area * * 2: "position 10: a value expected, not '*'": the second star is the tenth character of the field). The new column's type is the one chosen in its row; the result converted to it (a text where a number is asked: an error naming the feature, as the Python caller's).

Its needs (§5): the columns its expressions read are asked to the reader, with the others used after it.

How: a small parser of our own, not Python's eval: an expression can only compute, never open a file or run a command; it is read once when the parameters change (its mistakes then), and evaluated per feature as a small tree of functions. In etl2d/expr.py, usable by any node (the Filter next, a custom node too).

Reprojector

From the system of the input (read from the source, or forced when a file says nothing or lies) to the one asked. The node shows the transformation PROJ chose and its accuracy, as carto2D's Map system dialog (its §70).

A point of the Grand-Place, from Belgian Lambert 72 to Belgian Lambert 2008
  1. In EPSG:31370: x = 148,900, y = 170,700.
  2. In EPSG:3812, with the transformation PROJ takes without extra grid files: x = 648,899.61, y = 670,700.27.
  3. The 500,000 m of difference are by design: Lambert 2008's false origin was moved so that no Belgian coordinate can be mistaken for a Lambert 72 one. What remains, −0.39 m and +0.27 m, is the change of datum (BD72 to ETRS89), as PROJ estimates it here; with the official grid it can differ by some centimetres. Which one PROJ used is what the node shows.

Clipper

A box (xmin, ymin, xmax, ymax, in the input's system), later a polygon. Several outputs, each used or not:

OutputWhat goes outGDAL's test
insidethe features entirely in the boxWithin
partialthe features across the edgeIntersects and not Within
outsidethe features entirely outDisjoint

And one option for the features across the edge: whole, or cut at the box (Intersection); "inside + partial, cut" is the usual "clip".

A pavement 200 m long that leaves the box by 30 m
  1. It touches the box and is not entirely in it: it goes out on partial.
  2. Whole: 200 m. Cut: 200 − 30 = 170 m, its end on the box's edge.
  3. A point exactly on the edge: Within says no (on the edge is not inside), Intersects says yes: partial. Said in the node's help, because it surprises.

Filter: the switch on attributes (FME's TestFilter) 0.4.0

One input; one output per rule, plus else. A rule is a name (its output's), a column, a comparison, a value. Each feature goes out on the first rule it meets, in the order of the rows, or on else if none: no code, and nothing lost, since what no rule takes goes somewhere visible.

The 1,356 buildings of the Grand-Place, by size (the rules, top to bottom)
  1. small: area < 50
  2. medium: area < 200
  3. else: the rest, 200 m² and more.
A building of 30 m² meets rule 1 first: small, although 30 < 200 is true too: the order matters, and it is what one would write by hand ("under 50; otherwise under 200; otherwise"). A building with no area (empty, NULL): no comparison is true on an empty value: else, where it is seen, not lost. Measured on the real 1,356 buildings (16 November, the GeoPackage made by etl2d itself: parcels, buildings, addresses, EPSG:3812), each output to its layer of one GeoPackage: 357 small, 802 medium, 197 else, 0.10 s. Their areas go from 4 to 4,347 m², none empty: here else holds only the large ones.

Said before running (§4): a rule on a column that does not arrive (renamed before, in Attributes), a number expected and "abc" given for a column of numbers, two rules of the same name, a rule named else: the node is red and says which rule. The structure of each output is the input's.

What it needs (§5): the columns its rules read, plus what the nodes after it need; the box of its outputs together (if one needs everything, everything). An output joined to nothing: its features are dropped, as the Clipper's (§9); kept (§9), they are written.

Ports made from the parameters. Until now a node's ports are fixed in its code (outputs = [...]). The Filter's depend on its rules: a node may give a method outputs_for(params), and the graph, the window and the run ask it instead of the fixed list. Renaming a rule in Properties renames its output and the links follow (small → tiny: the link to the Writer stays); removing a rule removes its links, and the log says which. The same mechanism serves later nodes with ports from their parameters: several layers into one map (the MapWriter, §13), a router by value.

In the window: two lines per rule, the panel being narrow: its name, with ^ v (move it up, down: the order matters) and x; then the column chosen in a list of the columns received, the comparison in a list, the value typed (none for is empty). "+ rule" adds one. A name typed is applied when the field is left: its links follow then; a name already taken (or empty) is refused, the rule keeps its old name and the log says why. A rule removed: its links go, the log says which ("link #2 Filter small > #3 removed: no output 'small' any more"). A new rule on a column of numbers says "no value yet" in red until it has one.

Not found: red before the run.

The 197 large buildings of the Grand-Place (the Filter's else, §7): Reader buildings → Filter → else → MapWriter large.png, no style, no box: render2d draws the 197 in its default style, the area of the 197 plus 5 %, 1600 pixels wide. Then a page: large.pdf, A4-landscape, 1:2500, title "Large buildings, Grand-Place": the same features on a printed page with its legend line "large buildings". Measured (16 November, render2d 0.5.11): both maps from the one else output (a fan-out, §9) in 0.69 s for the whole run, reading included: large.png 1600 × 1182 pixels, 398 kB; large.pdf 48 kB, the title, the 1:2500 scale bar, the north arrow, the legend.

Later: one map per value of a column (group by: munniscode: one PDF per municipality, the value in the title); several layers on one map (several inputs, ports made from the parameters as the Filter's); the YSLD read to ask only the columns it uses.

Python caller

A function written in the node (or a file), called for each feature:

def process(feature):
    feature.attributes['street'] = feature.attributes['street'].title()
    if feature.attributes['POLICENUM'] in ('', None):
        return None              # dropped
    return feature               # or a list: several features out

An error in the function stops the run and shows the feature that caused it (its fid, its file, its attributes): the common case is a value nobody expected. The new columns it adds are declared in the node (their names and types), so that the structure still travels before the data (§4).

Writer

A format (any GDAL driver that writes), a file or a connection, a layer or table name, and a mode: create (refused if it exists), replace, append. A run that fails half way leaves what was there:

  • GeoPackage, SQLite, PostGIS: append adds in one transaction, rolled back on error. create and replace write into a new layer under a temporary name (parcels_etl2d_tmp), in one transaction; only when everything is written is the old layer dropped and the new one renamed. On error the new one is dropped, and a file the writer had created is removed.
  • Formats without transactions (shapefile, FlatGeobuf, GeoJSON): written in a temporary folder beside, moved in place at the end. For a shapefile only its own parts move (.shp, .shx, .dbf, .prj, .cpg, the indexes): a parcels.yaml beside parcels.shp is never touched.

It counts what it wrote, and says what the format changed (a shapefile cuts names to 10 characters, a GeoPackage does not).

Several layers into one GeoPackage (asked on 16 November: parcels, buildings and addresses in one file): one Writer per layer, the same path, each its layer name. A GeoPackage allows one transaction at a time ("database is locked" otherwise): writers into the same GeoPackage or SQLite file take turns during the run, the second starting when the first has committed (0.3.2; 1 test: 23). Each layer is safe on its own: if the third fails, the first two are written, the third is as it was. Later, perhaps, one Writer with several inputs (ports made from its parameters, as the Filter's). Two Writers on the same layer of the same file are refused before running (0.4.1): the layer left empty takes the file's name, so three Writers to grand-place.gpkg without a layer name would all write grand-place, each replacing or mixing the others' features (tried on 16 November: 7,220 parcels, buildings and addresses in one layer, points and polygons together). The second and third say "#20 Writer writes layer 'grand-place' of grand-place.gpkg too: give each Writer its own layer".

The spatial index of a GeoPackage (0.4.3): written without it (SPATIAL_INDEX=NO), then made once on the final layer, after the rename (CreateSpatialIndex()). GDAL's own, built during the transaction and carried through the rename, failed with the GDAL of Gohlke's wheels ("failed to execute insertion in RTree: UNIQUE constraint failed: rtree_parcels_etl2d_tmp_geom.id", 16 November: the first layer of three) though not with GDAL 3.8; made by us at the end, it works with both, and an index left by a killed run is dropped first.

8. Custom nodes: a Python file in a folder

As ComfyUI: at start, etl2d reads every .py file of nodes/ (its own) and custom_nodes/ (the user's), with importlib, and keeps every class marked as a node. The built-in nodes are found the same way: they are not special, they are the first examples.

from etl2d import node, Input, Output, Param

@node(name="Clipper", category="Geometry")
class Clipper:
    inputs  = [Input("features")]
    outputs = [Output("inside"), Output("partial"), Output("outside")]
    params  = [Param("box", "bbox"), Param("cut", "bool", default=True)]

    def schema(self, schemas):            # §4: the same structure on every output
        s = schemas["features"]
        return {"inside": s, "partial": s, "outside": s}

    def run(self, features):              # §3: one by one
        ...
  • The parameters become widgets in the node and in the properties panel: a "bbox" four numbers, a "bool" a checkbox, a "path" a field and a "…" button, a "crs" a field with carto2D's list of systems later.
  • "Reload" reads the files again: a node changed in a text editor is used at the next run, without restarting.
  • A file that does not load (a syntax error) is listed with its error in the log, and its nodes are absent; the others work.
  • A custom node runs with the user's rights, as a script would: only files one trusts go in custom_nodes/ (said in the README, as ComfyUI does).

9. One output, two nodes; looking inside

One by one has a price: an output joined to two nodes must give every feature to both. If the first asks for features faster than the second, the second's must wait somewhere.

  • In memory (itertools.tee): fine while the two read at about the same pace.
  • Beyond a limit (100,000 features waiting, to be measured), in a temporary FlatGeobuf, read back by the slower one.

Looking inside (step 4)

FME's best feature: what does this link carry? In etl2d, three pieces.

1. Keep an output ✓ 0.2.1. A right click on an output port (or on a link leaving it) ▸ Keep. What is kept is an output, not a link: every link leaving the same port carries the same features (§9 above), and an output joined to nothing can be kept too, to see what is thrown away. In the file: "keep": [[3, "outside"]] beside "links". The port's name turns blue, its links are drawn blue and thicker. From the command line too: run writes the kept files and says "kept #3 Clipper outside: 176,309 in …".

During the run, each feature passing a kept output is also written to a FlatGeobuf: job.etl2d/n3-outside.fgb, in a folder beside the workflow named after it (a work folder: to put in .gitignore, to delete when one wants). The file is written to a temporary name and renamed at the end; a stopped or failed run keeps the previous one, marked "old".

The price, measured on the test of §3 (16 November, 0.2.1: 200,000 addresses, Attributes dropping PARENTID, clipped to the Grand-Place, reprojected, written)
  1. Without keeping: the clip asks the reader its box (§5): 23,691 read: 23,675 inside, 16 partial (exactly on the box's edge: they touch it without being within), 1.50 s.
  2. Keeping inside: nothing changes upstream; the same 23,675 written once more: n3-inside.fgb, 3.6 MB (154 bytes a feature: 2 columns, a point, the spatial index), 1.66 s: 0.16 s more.
  3. Keeping outside: the outside is now used, so it needs everything (§5): the reader can no longer ask the box: 200,000 read, 176,309 outside, 27 MB written, 6.14 s: four times longer, because the reader reads eight times more. The reader's line "asks:" says it before the run ("asks: 2 of 3 columns", the box gone).
Keeping is a choice made where one wants to look, not everywhere.

2. The Table panel ✓ 0.2.1. A tab beside the Log, brought to the front when an output is kept, when a link of a kept output is clicked, or by its menu ▸ Show in the Table; a list chooses among the kept outputs. It shows the count, the time the file was written ("old" when the last run did not finish after it), the first 1,000 rows (read from the file by OGR, again when the file changes), the geometry as its type and size ("Point", "Polygon, 14 points"). Later: a click on a row selects that feature on the map.

3. The Map panel ✓ 0.3.0. A tab beside the Graph (dragged elsewhere if one wants both in view), showing the kept output the Table shows. render2d.exe draws the kept file: render2d n3-outside.fgb --bbox … --size 800x600 -o view.png, in a default style (or a YSLD chosen), on a basemap if one is chosen (basemaps/urbis-ortho-2024.xml: the addresses on the orthophoto). The image is shown in the panel and navigated as carto2D's map (its notes §9 to §11): during a drag or a wheel, the image is moved and stretched; at the end of the gesture, render2d draws again (a few tenths of a second, in a thread). The first view: the file's extent, plus 5 % (again with "whole", or a double click). Under the map: the scale, the mouse in the map's system, the time of the last drawing, what render2d said when it failed. The map's system is the file's (a file in degrees: EPSG:3857, as render2d does), given to render2d with --crs, so a basemap in another system is converted to it.

Measured (16 November, the 176,309 addresses outside the Grand-Place, 27 MB): the whole file, 1,000 × 650 pixels: 2.7 s; after six wheel turns (1:12,000 to 1:3,200), 0.22 s, because render2d asks the file's spatial index only for the view's box (the kept file is written with its index, SPATIAL_INDEX=YES). The image moved and stretched during the gesture is blurred (the old pixels, enlarged 3.8 times) until the new one comes.

Where is render2d.exe? Window ▸ Settings, once: its path (empty: the one on the PATH), and a basemap to draw under the kept file (empty: none). Remembered in settings.json in the user's settings folder, beside etl2d.ini. Without render2d, the Table works and the Map says where to set it.

Later (step 5): running from the middle. The kept files allow running again only what follows: a parameter changed after a kept output, and only the nodes after it run, reading the file instead of their sources (ComfyUI's cache, in files).

  • Adding: a click in the library puts the node in the middle of the view (several clicks: a staircase, not a pile); a right click on the graph's background opens the same list, and the node goes where the click was.
  • Joining: a drag from a port to another, either way. A link the graph refuses (an input already joined, a loop, two inputs) is said in a tooltip while dragging, and not made. The mouse resting on a link shows its schema (§4). Delete removes the link or node selected; F shows the whole graph.
  • Undo, redo, fit, box (0.4.2, asked on 16 November): Ctrl+Z and Ctrl+Y (or Ctrl+Shift+Z), also in Edit. Each frame where no gesture is going on (no mouse button held, no field being typed in), the workflow's text is compared to the last one; if it changed, the old one goes on the undo stack (200 deep). So every change is caught, wherever it was made (a node moved, a link, a rule, a paste), and a node dragged is one change, not sixty. Undo puts the old text back, positions included. Edit ▸ Fit the graph (or F) shows the whole graph; a drag on the background draws a box that selects the nodes in it, to move, copy or delete them together.
  • Copy, paste, duplicate (0.2.2, asked on 16 November): Ctrl+C copies the selected nodes (a Ctrl+click adds one to the selection, a drag on the background draws a box around several) with their parameters, the links between them and their kept outputs; Ctrl+V pastes them under new numbers, their top-left corner at the mouse (from the Edit menu: in the middle of the view); Ctrl+D does both, 40 points down and right. The links to nodes not copied stay behind: the pasted nodes say "input not joined" until joined. The clipboard holds the nodes as JSON, the same as a workflow file: they paste into another workflow, into another etl2d, or into a text editor to be read or sent; a whole workflow file's text pastes in too.
  • A node's title on a band of the colour of its category: readers green, writers brick, geometry blue, attributes ochre, Python violet, custom ones grey (0.3.0, asked on 16 November): the role of a node seen at a glance, even zoomed out. Joining, seen: while a link is dragged, over a port that accepts it the link turns green and says what would pass ("partial > features: 3 columns, Point, EPSG:31370"); over one that refuses, red, and why; once made, the link stays bright green for a moment.
  • Every change propagates at once: the schemas (§4) down, the needs (§5) up, before the next frame. Tried on the test of §3: joining the clip's outside to a Python caller turned the reader's line "asks: box 148500 170400 149300 171000, 2 of 3 columns" into "asks: 2 of 3 columns" (the outside needs everything, §5); ticking PARENTID again in the Attributes table made it "3 of 3 columns", and the writer's line "writes 4 columns". A node in error is drawn red and says why ("input not joined: features"); F5 then refuses and the log says which node. A text typed in Properties (a path, a connection, the Python code) propagates when the field is left or Enter pressed, not at each key (0.3.1): otherwise PG:host=… was tried at each letter, freezing the window while the server did not answer.
  • Properties: one widget per parameter type (§7): a path with "…" (a file dialog; the path is kept relative to the workflow's folder), a box as four numbers, the Python code on several lines, the columns as a table (keep, column, new name) made from the schema received, rows (name, type, width, value) with + and x, the columns read as boxes to tick. Under them: what the node receives and makes, column by column, and its notes.
  • Run: F5 or Run ▸ Run, in a thread; the window stays alive. The counts go green on each node (in, and each output) while it runs; the log gives the time and the rate. Esc stops between two features: the writers leave nothing (a test: neither the GeoPackage nor the shapefile made, no temporary folder left). Measured: the 200,000 points of §3, 23,691 features read, 2.07 s in the window against 1.15 s from a command prompt: the window takes its share of Python's time (one interpreter for both).
  • The file: the positions of the nodes are saved in the JSON (pos); a file written by hand, without them, is laid out by depth (readers at the left, writers at the right) and shown whole. The title bar says the file and a star when it has changed; Quit asks "Save first?". Ctrl+N, Ctrl+O, Ctrl+S.
  • The panels dock as in carto2D (hello_imgui); Window shows a closed one again, or the default layout. The layout is remembered in the user's settings folder (etl2d/etl2d.ini), not beside the workflows.

14. Decisions

#DecisionAlternative rejected
1Python all along: the window (imgui-bundle), the engine, the nodes (16 November).A C++ base (carto2D's window and map) with Python embedded for the nodes: two compilers (MinGW and MSVC) to reconcile, slower to change.
2A .venv with python.org's Python; GDAL from Gohlke's wheels.conda (another tool to learn); MSYS2's Python (imgui-bundle not packaged there).
3Features flow one by one (generators), as FME; files only where asked (kept links, fan-out beyond a limit).Whole layers between nodes through files: simple, but heavy in memory or on disk for large data, and unnatural for a per-feature Python caller.
4The structure travels before the data (schema(), then run()).The structure known only after a run: mistakes found late.
5The geometry stays an ogr.Geometry between nodes.Shapely or WKB between nodes: a conversion at every step.
6render2d.exe draws the previews, by files; render2d --serve or bindings only if measures ask.A map widget in C++ shared with Python.
7The needs come up from the writers to the readers (a box, columns), each node's needs(); a node without it needs everything (16 November, §5).The box copied by hand into the reader; every column always read.
8The window and the engine in one process, the run in a thread; the graph propagated again at every change (16 November, §11).The run in another process (as the command line): the window would not see the counts live; propagation on demand only: mistakes seen late.
9A Filter's outputs are named by its rules and follow them (renamed: the links follow; removed: they go, said) (16 November, §7).Outputs numbered (out1, out2): a rule moved would send its features elsewhere without a word.
