etl2d — Reading the code

A guide through the code, for someone who knows what etl2d does and wants to follow how. The notes (notions.en.html) say what and why; this page says where. Every name below is a file and a function you can open. The example all along is the workflow of the notes' §3: a Reader of 200,000 addresses, Attributes, a Clipper on the Grand-Place, a Reprojector to Lambert 2008, a Writer.

1. Three layers, one rule

The rule: the arrows only go down. The engine never imports the window (so python -m etl2d run works without imgui-bundle, and the tests run without a screen). A node imports only what etl2d/__init__.py exports: Input, Output, Param, node, Schema, SchemaError, Feature, Field; it knows nothing of the graph, the window, or other nodes. The engine does not import the nodes either: it finds them at start, in folders (§4).

Size, to know what you face: about 3,150 lines. The engine 920, the nodes 680, the window 1,460, the command line 90, plus 22 tests.

3. A node, opened

A node is a class with three lists and up to three methods. The Clipper (nodes/geometry.py), shortened:

@node("Clipper", "Geometry")                 # registry.py: puts a NodeSpec on the class
class Clipper:
    inputs  = [Input("features")]
    outputs = [Output("inside"), Output("partial"), Output("outside")]
    params  = [Param("box", "bbox", None), Param("cut", "bool", True)]

    def schema(self, schemas):              # §4: before any data. In: the inputs' Schemas
        s = schemas["features"].with_count(None)
        return {"inside": s, "partial": s, "outside": s}     # out: one Schema per output

    def needs(self, wanted):                # §5: in: what the nodes after it need, per output
        if "outside" in wanted:
            return {"features": Needs(None, columns)}        # out: what it needs of its input
        return {"features": Needs(its_box, columns)}

    def run(self, inputs):                  # §3: in: one iterator of Features per input
        def route(f): ...                   #   "inside", "partial" or "outside"
        return split(inputs["features"], route, [...], self.ctx.connected)   # out: one iterator per output

Before calling any of the three, Graph.instantiate() (graph.py) makes a fresh object and gives it four attributes:

  • self.params: its parameters, from the JSON file (with the defaults of params for those not given);
  • self.schemas_in: its inputs' Schemas (so run() can know the columns: Attributes uses it);
  • self.wanted: what the nodes after it need (a reader uses it to ask its source);
  • self.ctx: a Context: ctx.path() makes a parameter's relative path start at the workflow's folder, ctx.log() adds a note shown on the node, ctx.connected names its outputs that lead somewhere.

A reader has no input: its run({}) returns {"features": generator}. A writer has no output: its run() returns one generator, which writes a feature each time it is advanced (yield after each), and commits or rolls back in its finally. That is the whole contract; custom_nodes/README.txt shows the smallest node.

4. From the JSON file to a Graph

default_registry()                         registry.py
  └ load_folder("nodes/"), then "custom_nodes/"
      └ for each .py: importlib runs it; the classes marked by @node become NodeSpecs
        registry.specs = {"Reader": NodeSpec(...), "Clipper": NodeSpec(...), ...}

Graph.load("job.json", registry)           graph.py
  └ from_dict(data)
      ├ for each node:  NodeInstance(id=3, type="Clipper", params={...}, spec=registry.find("Clipper"))
      │                 a type not found: spec=None, kept and shown in red (its params untouched)
      ├ for each link:  Link(src=3, src_port="inside", dst=4, dst_port="features"), checked
      ├ "keep":         graph.keep = {(3, "outside")}
      └ order()         a loop refused here
  └ work_dir = job.etl2d/ beside job.json

A NodeInstance is the node in this workflow: its number, parameters, position, and what the last propagation said of it (schemas, given, wanted, asks, error, notes). The object of the node's class is made fresh each time it is needed (§3), and thrown away: it keeps nothing between two calls.

5. Before running: propagate() and plan_needs()

Two passes over the nodes, in graph.py. Neither reads a feature.

propagate() goes down, in order() (each node after those it reads from). For each node: the Schemas of the outputs it is joined to become its given; instantiate(inst).schema(given) gives its schemas. A SchemaError becomes its error, and the nodes after it get "waits for #3 Clipper".

plan_needs() goes up, in reverse order. For each node: what its consumers asks becomes its wanted (several consumers: union(); a kept output: everything); needs(wanted) gives its asks.

On the example (what each NodeInstance holds after the two passes)
  1. propagate, down: #1 Reader schemas = {features: 3 columns, Point, EPSG:31370, 200,000} → #2 Attributes drops PARENTID, renames STRNAMEFRE: 2 columns + source added = 3 → #3 Clipper: the same on its three outputs → #4 Reprojector: EPSG:3812 → #5 Writer: no output, a note "writes 3 columns…".
  2. plan_needs, up: #5 Writer asks everything → #4 Reprojector's wanted = everything, it asks the same → #3 Clipper's wanted = {inside: everything} (only inside is joined): it asks its box, all columns → #2 Attributes knows source is its own and PARENTID is dropped: it asks the box and STRNAMEFRE, POLICENUM → #1 Reader's wanted = box 148500 170400 149300 171000, 2 of 3 columns: the line "asks:" on the node.

The window calls both after every change (State.refresh()); the command line once, before printing each node; run() once more at its start.

6. The run: generators, then the pull

run() (run.py) has two halves, and the key to it is that the first half runs nothing.

First half: build. For each node in order: obj = instantiate(inst); its inputs are taken from outputs[(src, port)] (the iterators made by the nodes before it); obj.run(inputs) returns generators. A Python generator does nothing until asked for its next value: calling run() on all five nodes takes microseconds and reads no feature. Around each output, two wrappers: _counted() (the green counts) and guarded() (an exception becomes a RunError naming the node). An output joined to two nodes is split by itertools.tee; a kept output gets one more consumer, keeper(), added to the sinks. A writer's generator goes to sinks.

Second half: pull.

while active:                      # the sinks not finished yet
    if stop.is_set(): raise RunError("stopped")
    for sink in active:
        next(sink)                 # one feature through, from the reader to this writer

Each next() on a writer asks its input for one feature, which asks its own input, and so on up to the reader, which asks OGR. Several sinks are pulled in turn, so the queues of a tee stay short. When a sink is exhausted (StopIteration), it has committed. On an error, the other sinks are close()d: their finally rolls back.

7. One feature, followed

One next() on the Writer, on the example; read it from top to bottom, then back up:

run.run          next(writer)
writers.py         write(): for feat in inputs["features"]      → asks the Reprojector
geometry.py          Reprojector gen: for f in inputs[...]      → asks the Clipper
run.py                 split().pull("inside"): queue empty      → reads from its input
attributes.py            Attributes gen: for f in inputs[...]   → asks the Reader
readers.py                 features_of(): for f in lyr          → OGR: the next row in the box
                           yield Feature({"STRNAMEFRE": "rue au Beurre", "POLICENUM": "12"}, POINT, 2, "addr.gpkg")
attributes.py            f.attributes = {"street": "rue au Beurre", "POLICENUM": "12", "source": "UrbIS 2026"}; yield f
run.py                 route(f) = "inside": into the inside queue; pull("inside") yields it
geometry.py          f.geometry.Transform(31370 → 3812); yield f
writers.py         lyr.CreateFeature(...); yield        ← next() returns here

Only one feature is in flight at a time (plus the few waiting in a queue of split() or tee): 200,000 features or 20 million, the memory is the same. A feature routed to "partial" while "inside" asks waits in the partial queue, if partial is joined; else it is dropped (§9).

8. The window: one frame

hello_imgui calls the program about 60 times a second (fewer when nothing moves). Each frame, in app.py:

App.menus()            File, Edit, Run, Window; the file name and "running…" at the right
App.every_frame()      the Table to the front if another kept output was chosen;
                       shortcuts() (Ctrl+S, Ctrl+C, F5…); the quit question; the Settings window
then each panel's function, for the panels shown:
  _library(state)        Nodes: a click → editor.add_node()
  editor.draw(state)     Graph: state.refresh() first, then nodes, links, gestures
  properties.draw(state) Properties of state.selected
  map.draw(state)        Map of state.looked
  table.draw(state)      Table of state.looked
  _log(state)            Log: state.log

Dear ImGui is "immediate": nothing is kept on the screen between two frames; every panel is drawn again from State each time. So a change is simply: change State (or state.graph), and set state.dirty_structure = True when the structure may have changed; at the next frame editor.draw() calls state.refresh() (propagate() and plan_needs()) and every panel shows the new state. A parameter typed in Properties, a link dragged in the Graph, a node pasted: the same path.

In editor.draw(), the order matters to imgui-node-editor: ed.begin(); each node (_node(): begin_node, its pins, its text, end_node, then its title band drawn behind); each link; then the gestures: begin_create() (a link dragged: green or red, accepted or refused by Graph.can_link()), begin_delete() (Delete), the selection, the right-click menus; ed.end(). Pins are numbered node×1000 + 1 + i for inputs and node×1000 + 500 + i for outputs: port_of() turns a pin number back into (node, port).

9. Threads: the run and render2d

Two things would freeze the window if done in a frame, so each goes to a thread:

  • The run (State.start_run()): a thread calls run(graph, live=state.live, stop=state.stop). run() fills live at its start with each node's counters (lists of one int, changed in place by _counted()); editor._node() reads them each frame: the green counts. Esc sets state.stop, checked by the pull loop between two features. While state.running, the editing is refused (no link, no delete, Properties greyed): the graph is in use.
  • render2d (MapView.start()): a thread runs render2d.exe (subprocess), reads the PNG it wrote, and leaves its bytes in self.done. The next frame, in the window's thread (the only one allowed to touch the GPU), turns them into a texture. Between two drawings, MapView.draw() moves and stretches the last texture with the mouse.

Python runs one thread at a time (the GIL): the window and the run share it. That is why a run in the window takes longer than from the command line (§11 of the notes: 2.07 s against 1.15 s).

11. An order to read it in

  1. etl2d/feature.py, schema.py, needs.py: the three small data types (20 minutes).
  2. nodes/attributes.py: the simplest node with an input, its three methods; then nodes/geometry.py, the Clipper, and nodes/filter.py, the Filter (its rules made once into small functions, then route()); nodes/validator.py, the GeometryValidator, the same split() with three fixed outputs; nodes/relator.py, the SpatialRelator, two inputs: the reference read whole into a grid (etl2d/index.py) at the first feature asked, then the features streamed.
  3. etl2d/registry.py: how @node and the folders make the library.
  4. etl2d/graph.py, propagate() and plan_needs(), with §5 of this page beside.
  5. etl2d/run.py, run(), with §7 of this page beside: the heart. Try it: a print() in Attributes' gen() and in the Writer's write(), then etl2d.bat run on a small file: the prints alternate, one feature at a time.
  6. nodes/readers.py and nodes/writers.py: the parts that touch GDAL.
  7. ui/state.py, then ui/app.py, then ui/editor.py: the window, once the engine is clear.
